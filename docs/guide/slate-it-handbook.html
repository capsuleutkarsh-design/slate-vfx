What the studio is made of

Slate has three parts. One server PC runs Slate Server and keeps the studio database on its own disk. One shared folder on the network, called Slate_Central, holds files every PC needs. Every other PC is a workstation with Slate Studio, Slate Operations, or both.

Two folders called Slate_CentralThe shared Slate_Central is on the network, for example Z:\Slate_Central or \\server\share\Slate_Central. The server PC also has a local folder with the same name, %LOCALAPPDATA%\Slate_Central. That local one holds the database, the backups and the Recovery Key's fingerprint. Never mix them up, and never delete the local one.

Setting up a brand-new studio

Do these in this order. The order matters: the server must exist before any workstation can sign in, and the first Slate that opens builds the studio's tables and roles.

1. Install Slate Server

  1. Pick the server PCAlways on, wired network, a fixed address (a DHCP reservation). The database lives on its own disk.
  2. Run the server installersetup_Slate Server_vBETA 2.2.0.exe. Sign in to Windows as the account that will run the server every day.
  3. Select Slate_Central Shared FolderType the shared folder in Server Root Path, e.g. Z:\Slate_Central. It cannot be left blank. Use the same path on every PC.
  4. FinishThe Start menu now has Slate Server and Recover Slate.
"This folder does not exist on this machine"The installer asks Use it anyway? when it cannot see the shared folder. Answer Yes only if the drive is simply not mapped yet. If it is a typo, answer No and fix it. A wrong path means Slate works on that PC only and shares nothing.

2. First start: where the database lives

Open Slate Server. It opens on the Dashboard. If you want the database somewhere other than the default %LOCALAPPDATA%\Slate_Central\LocalDatabase (for example a second internal drive), go to Settings first, type it in Database folder, and press Save Configuration. Keep it on this PC's own disk: Recover Slate refuses a database on a network drive.

  1. Database Server PowerTurn the switch on. The badge says Starting..., then Server Online.
  2. Read SYSTEM LOGSA new studio shows: "This studio's own database password was made and is kept on this PC only."
  3. Tables in Database: 0Normal now. The warning "exists but has no tables" goes away when the first workstation opens Slate.

3. The Recovery Key

Right after the database starts for the first time, Slate Server shows Your Slate Recovery Key. It looks like XXXXX-XXXXX-XXXXX-XXXXX-XXXXX. It is shown once. Slate keeps only a one-way fingerprint of it, so nobody can read it back later.

Never lose the Recovery KeyIt is the only way back in when nobody can sign in. If it is lost, a Windows administrator on the server PC can make a new one: right-click Recover Slate, Run as administrator, leave the key box empty and press Make a new Recovery Key. The old key stops working at once. Without the key and without Windows administrator rights on the server PC, there is no way back.

4. Open the firewall

  1. Settings → Allow FirewallWindows asks for administrator rights. Say yes.
  2. Check the log"Firewall rules are in place; workstations can connect." Beside the buttons: Firewall allowed.
  3. Firewall not changedThe request was refused. Press it again, or add the three rules by hand.

The studio's database password

Every workstation signs in to the database with one shared account, ut_vfx_app, and one password. People's own Slate passwords are separate: this one is only between the PCs and the server.

  • Each studio has its own. Slate Server makes a strong random one when it creates a new database. No password ships with Slate any more.
  • On the server PC it is kept encrypted by Windows, in slate_recovery\db_secrets.dat beside the database. Only this PC can read that file.
  • On a workstation it is kept in Windows Credential Manager (a generic credential named Slate, user db_password), not in a settings file.
  • You read it in Recover Slate: Database passwords → Show app password. Write it down and keep it with the Recovery Key. You need it again if you ever move the server.

A database that still uses the old shared password

Every Slate before 2.2.0 shipped with the same database password, and it is public. When Slate Server 2.2.0 starts on such a database, it keeps that old password working for now and publishes a new one of the studio's own. The log says "This studio still uses the database password older Slate versions shipped with." The health check in Recover Slate warns Studio password until you switch.

Recommended first step when no PC is running Slate yetIf your server already has its database from an older Slate, and no workstation runs Slate yet, switch to the studio's own password now, before you set up any workstation. Nobody is using the old one, so nobody can be cut off, and every workstation you set up afterwards gets the new password from the start.

Then set up the workstations with the password Show app password now gives. If you ever need to go back, Show app password also prints "Before the last change it was: ...". Type that one in the two password boxes and press Set app password (workstations).

The same switch on a studio where workstations are already running

Do not switch straight away. First get every workstation on 2.2.0 and open Slate on each once: each one learns the published password quietly. Show app password lists the ones that have it, under "Workstations that have it". When every PC is listed, press Switch to the published password at a quiet moment. Anyone who had Slate open may need to restart it. A PC that missed it says it has no password: use Reconfigure server / database on its sign-in screen.

Do not use Settings to change the passwordTyping a new password into Slate Server's Settings → Database password and saving changes it for the server at once, and cuts off every workstation that does not have it. The gentle way is always Recover Slate: Publish, then Switch.

The first administrator, people and roles

The first workstation

  1. Install on your own PCSlate Operations (and Slate Studio if you want it). The installer asks for the same Server Root Path as the server.
  2. Set up Slate on this computerOpens at the first start. Find server, type the database password, Test connection, Save.

Make your administrator

A new database starts with one account, admin, with the Developer role (full access), while the switch no_default_accounts is off (it starts off). Its starter password is the well-known admin123, so Slate marks it: the first sign-in must choose a new password before anything opens. The same happens if Slate ever brings admin back after it was removed. Sign in as admin yourself, straight away, before you set up any other PC:

  1. User name adminOn your workstation's sign-in window. Password admin123. Press Sign in.
  2. Choose your passwordOpens by itself. Your own password twice, 8 or more characters. Save password.
  3. Keep it with the keyWrite the admin password down with the Recovery Key. Cancel on that window only goes back to sign-in.
  4. Create peopleIn Users & Roles, below. Give yourself a personal account too, and keep admin for emergencies.
The other way in: Recover SlateOn the server PC: Recovery, type the Recovery Key, Unlock. In Accounts type a username (blank means admin) and a new password twice, then press Create or restore administrator. The output says "...is an active administrator again, with the new password." or "Created the administrator ... with the new password." That person chooses their own password at the next sign-in. This works at any time, even before any workstation has opened Slate: a new studio always gets its starting roles (Supervisor, Lead, Coordinator, Artist and the rest), whoever made the first account.
With no_default_accounts onNo starter account is ever made or brought back. The first-run notice then says "To make the first administrator, open Recover Slate on the server PC and use Accounts > Create or restore administrator." Type any username there; Slate creates it with the Developer role.

Publishing updates

From 2.2.0, the update is the installer itself. You install Slate by hand once. After that, you publish the new installers on Slate Server and every workstation updates itself from the shared folder.

Publish an update, step by step

  1. DownloadThe new setup_Slate_Studio_v….exe and setup_Slate_Ops_v….exe from the owner's GitHub release, onto the server PC.
  2. Back up nowOperations. A new version may change the database the first time a workstation opens it.
  3. Required?Tick Required (installs even if the artist chose later) before publishing, if nobody may put it off.
  4. Publish update…Settings. Choose one or both installers. Any other file name is refused.
  5. Read the result"Slate Studio BETA … is now offered to every Slate Studio workstation." and the folder.

Slate Server copies each installer into Slate_Central\Updates\releases, checks the copy, then writes manifest_studio.json or manifest_ops.json beside it, then deletes that program's older installers. Installers are hundreds of MB, so this takes a while; the line above the buttons shows each step.

What the artist sees

  • Within 5 minutes Slate finds the update (10 seconds after start, then every 5 minutes). To spare the network, each PC first waits a random time of up to 10 minutes, then copies the installer in the background.
  • A new version of Slate is ready. Update now asks about unsaved work, closes Slate, installs and opens Slate again. When I close Slate installs it at the next real close (not a sign-out); Slate then does not reopen by itself.
  • If an update is made required while the ordinary offer is still open on a PC, the countdown replaces that offer. The silent installer starts only once Slate has fully closed.
  • Settings → Check for updates looks at once, without the wait, and always says what it found.
  • A copy whose checksum does not match is deleted and never installed: "...is not the file that was published (its checksum does not match)...".

Recover Slate and the security switches

Recover Slate is for when nobody can sign in, or a security change went wrong. It works only on the server PC, and only with the Recovery Key. It never needs a Slate password or a database password.

Open it from the Start menu (Recover Slate), or click Recovery in Slate Server's left-hand list. Both show the same page. The Start-menu one works even when the Slate Server window will not start. It refuses to run on any other PC, or against a database on a network drive.

The never-lock-out rules Every switch starts Off. A snapshot is taken before every change and every repair, so each can be undone. Turn on first checks that people can still get in, refuses if not, and undoes itself if the check afterwards fails. Turn off works even when the database is down. Every action is written to slate_recovery\recovery.log, never with a password or the key.

Moving the server to another PC

  1. Old PC: Back up nowCopy the .dump away. Note the app password (Show app password).
  2. Turn the power offThen copy the whole folder that holds LocalDatabase, Backups and slate_recovery.
  3. New PC: install, pointInstall Slate Server. Turn on the power and choose Use an existing database folder...: the copied LocalDatabase.
  4. Give it the passwordThe new PC cannot read the old PC's encrypted passwords. Recover Slate, Unlock, type the noted password, Set app password (workstations), Restart pool.
  5. Allow FirewallOn the new PC. Then Check now in Recover Slate.
  6. Point the workstationsGive the new PC the old address, or use Reconfigure server / database on each workstation.

Instead of copying the folder you can create a new empty database on the new PC and use Restore from file… with the dump. Workstations never follow a moved server by themselves: a PC keeps the server it was set up with, so another PC answering on the network cannot take its place.

Never run two servers on the same dataTwo servers mean two sets of changes nobody can merge. Old one off, then new one on. Keep the old PC's folder untouched until the new one has run for a week.
